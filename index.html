또롱이는 일반 사용자와 비회원이 웹에서 자전거를 조회하고 대여·반납할 수 있으며, 운영자와 관리자가 자전거·대여 정보와 운영 자료를 관리할 수 있도록 구성한 공공자전거 서비스입니다.

단순한 웹 기능 구현에서 끝내지 않고, 외부 사용자의 요청이 네트워크와 보안 장비를 거쳐 웹 서버와 데이터베이스까지 전달되는 환경을 구성했습니다. 그 위에서 웹 취약점과 운영상의 보안 문제를 재현하고, 탐지·차단·보완 후 동일한 요청을 다시 수행해 대응 여부를 확인했습니다.

Project 03 · Security Validation

문제를 재현하고, 막은 뒤 다시 확인했습니다

04

구축한 공공자전거 서비스에서 접근제어, QR 토큰, 운영자료 접근, 감사 로그와 관련된 문제를 시나리오로 재현했습니다. 대표 사례는 요청이 어디에서 발생하고 어떤 계층에서 대응했는지까지 흐름으로 정리했습니다.

A01 · REPRESENTATIVE CASE

IDOR 접근제어 문제

사용자 식별값을 변경했을 때 다른 사용자의 대여 정보를 조회하거나 강제 반납할 수 있는 문제를 확인했습니다.

01 · REPRODUCE 요청 값 변경

대여 조회·반납 요청의 사용자 식별값을 변경해 타 사용자 데이터 접근 가능 여부를 확인했습니다.

02 · FIX Flask 권한 검증

요청 사용자와 대여 정보의 관계를 확인하도록 서버 측 접근제어 로직을 보완했습니다.

03 · DETECT WAF · Wazuh

관련 비정상 요청과 애플리케이션 이벤트가 탐지되도록 보안 계층을 구성했습니다.

04 · RETEST 동일 요청 재수행

같은 방식으로 다시 요청해 타 사용자 정보 접근이 제한되는지 확인했습니다.

A02

QR Token 변조

예측 가능한 대여 토큰의 변조 가능성을 확인하고, 토큰 검증과 재사용 방지를 적용한 뒤 WAF · Snort · Wazuh에서 관련 이벤트를 확인했습니다.

A04

운영자료 비인가 접근

인증 없이 접근 가능한 운영자료 경로를 확인하고, 접근 정책을 수정한 뒤 Snort · WAF · pfSense에서 관련 접근을 제한했습니다.

A05

감사 로그 부족

운영정보 변경 과정에서 필요한 기록을 정의하고, 감사 로그를 남기도록 보완한 뒤 Wazuh에서 로그 누락과 이상 이벤트를 확인했습니다.

07 · Problem Solving

문제를 해결하는 방식

09
STEP 01

흐름부터 확인

문제가 발생하면 시스템 전체 구조와 데이터가 이동하는 경로부터 확인합니다.

STEP 02

원인 범위 축소

파일, 권한, 경로, 서비스 설정, 네트워크 연결 등을 단계적으로 확인합니다.

STEP 03

다시 검증

설정을 변경한 뒤에는 동일한 조건에서 다시 테스트하여 실제로 문제가 해결됐는지 확인합니다.
